# From 1003 Queries to 4: Optimizing Django ORM Performance

Performance is something that's easy to overlook when building an application. Everything works fine with a small amount of data, but things can quickly change as the database grows.

While working on FinSight, I decided to investigate how Django handles queries when listing transactions.

## The problem

I wanted to test how the application performs when working with a larger number of transactions.

For the experiment, I used 1,000 transaction records and inspected the database queries using Django Debug Toolbar.

The initial implementation generated **1003 SQL queries**, including 1000 duplicate queries.

The total execution time was **389.17 ms**.

## The optimization

The issue was related to how associated objects were retrieved when listing transactions.

To reduce unnecessary database queries, I used Django ORM's `select_related()` and `prefetch_related()`.

These methods allow related objects to be loaded more efficiently instead of generating additional queries for individual records.

## The results

After the optimization, the results were considerably better:

| Metric | Before | After |
|---|---:|---:|
| SQL queries | 1003 | 4 |
| Execution time | 389.17 ms | 18.15 ms |

That's a reduction from 1003 queries to just 4.

The measured execution time also dropped significantly.

## Conclusion

This experiment demonstrated how important it is to understand what happens behind Django ORM queries.

An implementation can work perfectly from a functional perspective while still generating unnecessary database traffic.

Using `select_related()` and `prefetch_related()` helped me significantly reduce the number of queries and improve performance when listing transactions.
